## 1. 설치 위치 파악 (교체 전)
1. 감시 스택에 서버 등록(IIS/WAS 포함 `host:port`). 포트를 여러 개 쓰는 서버는 모두 등록.
2. 인벤토리 확인
   ```bash
   cd monitoring
   python scripts/cert_inventory.py serials          # 현재 인증서의 일련번호와 서버 수
   python scripts/cert_inventory.py list
   ```
3. **교체 대상 일련번호**를 정하고 스냅샷 저장
   ```bash
   python scripts/cert_inventory.py snapshot --serial <일련번호> -o before-2026-11.csv
   ```
4. 감시에 잡히지 않는 곳 확인(포트 미개방 서비스, 메일 STARTTLS, 로드밸런서·WAF·방화벽 장비, 임베디드 장비 등) → 수동 목록에 추가
5. 서버별 담당자·재기동 영향·점검 시간대를 표로 정리(서비스 중단 허용 범위 사전 합의)

## 2. 교체 전 준비
- [ ] 새 인증서·개인키·체인(중간 CA)이 한 세트로 준비됨(`fullchain` 순서: 서버 → 중간 CA)
- [ ] 개인키 보관: 권한 600, 필요한 서버에만 전달, 전달 경로 암호화(SSH), 채팅·메일 금지
- [ ] 기존 인증서·키·설정 파일 **백업**(서버별 `.bak-날짜`)
- [ ] 롤백 방법 확인(백업 복원 + 서비스 재로드)
- [ ] 와일드카드 범위 확인: 새 인증서 SAN 에 `*.도메인` 과 루트 도메인(필요 시)이 모두 포함되는지

## 3. 서버별 교체 절차 (한 대씩)
1. 새 인증서·키 배치(권한 확인) → 설정 문법 검사(`apachectl configtest` 등)
2. 서비스 재로드(가능하면 reload, 불가하면 점검 시간대에 재기동)
3. **즉시 확인**
   ```bash
   echo | openssl s_client -connect <호스트>:<포트> -servername <호스트> 2>/dev/null | openssl x509 -noout -serial -enddate -subject
   ```
   일련번호·만료일이 새 인증서인지 확인
4. 감시 화면 반영 확인(최대 5분): 대시보드 "최근 7일 내 발급된 인증서" 표에 나타남
5. 문제 시 즉시 롤백 → 원인 정리 후 재시도

서비스별 참고(제품 문서로 최종 확인 필수)
| 서비스 | 형식·재적용 |
|---|---|
| Apache httpd | PEM(`SSLCertificateFile`/`SSLCertificateKeyFile`/체인), `reload` |
| Tomcat | PEM 직접 참조 또는 PKCS#12/JKS 변환. 버전에 따라 재로드 가능 여부 상이 |
| WebtoB / JEUS | 제품 고유 설정. **벤더 문서·기존 설정 확인 후 진행** |
| IIS | PFX 가져오기 → 바인딩 교체(`certdeploy/deploy-iis.ps1` 초안, certdeploy 자동 배포 대상 아님) |
| Node.js | PEM 교체 후 재시작(프록시 뒤라면 프록시 인증서만 교체) |
| 로드밸런서/WAF | 해당 장비 콘솔에서 별도 교체(감시 대상에 장비 VIP 등록) |

## 4. 전체 검증
```bash
python scripts/cert_inventory.py check --snapshot before-2026-11.csv -o result-2026-11.csv
```
- 종료 코드 0(미교체·조회 실패 없음)이면 완료. 1 이면 표의 미교체·조회 실패 서버를 조치.
- Grafana "같은 인증서를 쓰는 서버 수" 에서 **옛 일련번호가 0대**인지 확인.
- 알림 확인: 옛 인증서 관련 경보가 해소(resolved) 처리되는지.
