# CertPilot 제품 방향·로드맵 (제안 v1)

> **현재 상태 (2026-10-28)**: 감시 스택·`certdeploy`(자동 발급·수동 가져오기·자동 배포·웹방화벽 API)의 코드와 자동 테스트가 완료되었고, 실제 VM·장비 검증 전이다. 문서 목차 [docs/README.md](README.md), 준비 [pre-vm-checklist](ops/pre-vm-checklist.md), 검증 현황 [verification-report](ops/verification-report.md).

> **결정 (2026-10-28, 오너): 감시는 Prometheus + ssl_exporter + Grafana 오픈소스 스택으로 진행한다.** → [`monitoring/`](../monitoring/README.md)
> CertPilot(이 저장소의 Flask 앱)의 개발은 **보류**한다. 코드·테스트·문서는 그대로 보존하며, SSH 디스크 파일 인벤토리·감사 로그·교체 체크리스트 워크플로가
> 꼭 필요해질 때 아래 Phase 0 부터 재개한다. 이 문서의 이하 내용은 재개 시 참고하는 계획이다. 발급·배포·갱신은 [갱신 자동화](ops/acme-automation.md) 참고.

작성 기준: 2026-10-28. 이 문서는 **제안**이며, PRD 범위를 바꾸는 항목은 오너 승인 후 PRD 개정(v0.4)으로 반영한다.
관련: [PRD](PRD.md) · [ARCHITECTURE](ARCHITECTURE.md) · [TRACEABILITY](TRACEABILITY.md) · [OPEN_ITEMS](OPEN_ITEMS.md)

## 1. 진단: 무엇이 진짜 문제인가

| 사실 | 의미 |
|---|---|
| 교내 서버 50대 이하, Linux 중심 + Windows 소수 | 대규모 CLM 은 과잉. 가볍고 정확한 인벤토리·감시가 핵심 |
| Apache / Tomcat / WebtoB·JEUS / IIS / Node.js 혼재 | **SSH 파일 조회만으로는 부족.** 실제로 서비스되는 인증서를 보는 TLS 포트 조회가 OS·제품 무관하게 통한다 |
| 와일드카드 RapidSSL 가 **2026-11-12 만료** (발급 2026-04-27, 약 199일) | 인증서 수명 상한이 이미 200일이고 **2027-03 이후 100일, 2029 년 47일**로 단축 → 연 1회 수동 교체 불가, 자동화 필수 |
| DNS 는 Infoblox, 와일드카드 사용 | 자동 발급은 DNS-01 방식이 필요 (Infoblox WAPI/RFC2136, 하위 영역 위임) |
| CertPilot 은 현재 **조회·만료 상태 확인**만 가능, 일회성 수동 조회, 알림 없음 | 사고를 막으려면 "알려주는" 기능이 가장 부족하다 |

**핵심 문제는 "인증서를 못 만드는 것"이 아니라 "어디에 무엇이 깔려 있고 언제 만료되는지 사람이 계속 확인해야 하는 것, 그리고 갱신이 조용히 실패해도 모르는 것"이다.**

## 2. 방향 결정 (권고)

1. **CertPilot 은 '감시·인벤토리·갱신 검증' 도구로 유지한다.** 발급·배포는 검증된 오픈소스(lego/certbot, Infoblox 연동)에 맡기고 CertPilot 은 개인키를 다루지 않는다.
   - 이유: 발급·배포는 쓰기 권한과 개인키 취급이 필요해 현재의 보안 모델(읽기 전용, 키 미접근)과 충돌하고, 이미 성숙한 도구가 있다.
   - 대신 CertPilot 이 **"갱신이 실제로 서비스에 반영됐는가"를 독립적으로 검증**한다. 자동 갱신 실패를 가장 먼저 잡는 위치다.
2. **TLS 엔드포인트 조회를 1순위 방식으로 승격한다.** SSH 파일 조회는 "서비스되지 않는 인증서·갱신 파일 점검"용 보조 수단으로 둔다.
3. **알림과 주기 조회를 P1 에서 P0 으로 올린다.** 감시 도구가 사람이 눌러야만 동작하면 사고를 못 막는다.
4. **설치 위치를 지문(SHA-256) 기준으로 묶어 보여준다.** "이 인증서를 쓰는 서버가 어디인가"가 교체 작업의 핵심 질문이다.
5. **배포 위치를 결정한다**(§6 D-1). 교내 사설망 서버를 조회하려면 CertPilot 도 교내망에서 돌아야 한다.

비목표(당분간): 내장 ACME 발급, 인증서 자동 배포·교체, Windows 인증서 저장소 조회, bastion, 쿠버네티스.

## 3. 단계별 계획

### Phase 0 — 만료 사고 방지용 최소 기능 (약 1주, 2026-11-12 대응)
목표: 이 인증서가 **어디에 설치돼 있는지 100% 파악**하고, 교체 후 **빠짐없이 바뀌었는지 확인**한다.

| # | 항목 | 크기 | 완료 기준 |
|---|---|---|---|
| 0-1 | OS 선택 UI 마무리(백엔드는 완료) | S | 등록 화면에서 OS 선택, 감지 결과·불일치 표시 |
| 0-2 | **TLS 전용 서버 등록**(SSH 계정 없이 `host:port` 만) + CSV/붙여넣기 일괄 등록 | M | 50대를 한 번에 등록, Windows·IIS·WAS 포함 |
| 0-3 | **인증서 그룹 뷰**: 지문별로 설치 위치 목록, 와일드카드·SAN, D-day | M | "RapidSSL 인증서가 설치된 서버 N대" 한 화면 |
| 0-4 | **교체 체크리스트**: 대상 인증서 선택 → 서버별 "교체 완료/미완료"(새 지문 감지) 표시, CSV 내보내기 | M | 교체 후 재조회로 미완료 서버가 즉시 보임 |
| 0-5 | 이메일 알림(SMTP) + 임계값(30/14/7/3/1일) + 중복 억제 | M | 만료 임박 시 담당자 메일 1회/단계 |
| 0-6 | 주기 조회(일 1회, 만료 임박 서버는 시간 단위) | M | 사람이 누르지 않아도 최신 상태 유지 |

### Phase 1 — 안정 운영 (2~4주)
| # | 항목 | 비고 |
|---|---|---|
| 1-1 | 조회 이력 저장(서버·인증서별 지문 변경 이력) | 교체 이력, 갱신 주기 확인, 장기 보관(PRD P1) |
| 1-2 | 비동기 조회 작업 큐(`POST /scan` → 202 + 진행 조회) | OPEN_ITEMS I-3 |
| 1-3 | 웹훅 알림(Teams/Slack/Mattermost 등), 확인(ack)·보류(snooze) | 알림 피로 방지 |
| 1-4 | **서비스 프리셋**: Apache/Tomcat/WebtoB·JEUS/Node.js 설치 경로를 입력하면 알려진 하위 경로를 후보로 제시 | 제품별 기본 경로는 제품 문서로 확정 후 반영(추정 금지) |
| 1-5 | KPI 집계(AC-9), 주기 감사 무결성 검증 + 알림(AC-10) | TRACEABILITY 의 ❌/🔶 해소 |
| 1-6 | 만료 캘린더·타임라인 화면 | 갱신 작업 계획용 |
| 1-7 | 교내 계정 연동(LDAP/OIDC/SAML 중 택1) | 사용자 직접 관리 부담 제거, D-3 |

### Phase 2 — 갱신 연동 (4~8주, 선택)
CertPilot 이 발급 도구를 **대체하지 않고 감독**한다.
| # | 항목 | 설명 |
|---|---|---|
| 2-1 | **갱신 훅 수신 API** `POST /events/renewal`(서명 토큰) | lego/certbot 배포 훅이 "갱신 완료/실패"를 보고 → 감사 로그·화면에 기록 |
| 2-2 | **배포 검증** | 갱신 보고 후 서비스 엔드포인트를 재조회해 새 지문 확인, 미반영 서버 경보 |
| 2-3 | **갱신 지연 경보** | 갱신 예정 시점(예: 발급 후 60일)이 지나도 새 지문이 안 보이면 만료 한참 전에 경보 |
| 2-4 | **갱신 준비 점검** | Infoblox 위임 CNAME 존재, 발급 서버 상태 확인, 스테이징 발급 성공 여부 요약 |
| 2-5 | 갱신 런북 생성 | 서버별 재적용 방법(Apache reload, Tomcat 재로드, IIS 바인딩 등) 체크리스트 |

### Phase 3 — 보류 항목(수요가 확인되면)
내장 ACME 발급·배포(키 취급 보안 설계 선행, 별도 PRD), Windows 인증서 저장소 읽기(WinRM), 키스토어 내용 파싱(Q-KEYSTORE 독립 검토 필요), 고가용성.

## 4. 외부 도구와의 역할 분담

| 역할 | 도구 | CertPilot |
|---|---|---|
| 발급·갱신 | lego 또는 certbot(+ Infoblox WAPI/RFC2136, `_acme-challenge` 하위 영역 위임) | 갱신 훅 수신·준비 점검(Phase 2) |
| 배포·재로드 | 배포 훅 스크립트 또는 Ansible, IIS 는 win-acme/PFX 가져오기 | 배포 결과 검증(새 지문) |
| 감시·인벤토리·알림 | — | **핵심 기능(Phase 0~1)** |

대안 비교: Prometheus `ssl_exporter` + Grafana 는 TLS 만료 감시만 빠르게 구성할 수 있다. CertPilot 이 줄 수 있는 추가 가치는 ①지문별 설치 위치·교체 체크리스트 ②SSH 파일 조회(서비스되지 않는 인증서) ③감사 로그·권한 관리 ④갱신 검증이다. Phase 0 이후에도 이 차별점이 체감되지 않으면 ssl_exporter 로 전환하는 것이 합리적이다(검토 시점: Phase 0 종료).

## 5. 설계 원칙 (이후 모든 기능에 적용)
- 개인키는 읽지도, 저장하지도, 전달하지도 않는다(감시·검증 도구의 신뢰 근거).
- 화면에는 분류된 원인·조치 방향만, 원문은 감사 로그에만.
- 새 기능은 **요구 → 테스트 → 구현** 순서, TRACEABILITY 갱신 필수. "통과" 표기는 자동 테스트 근거가 있을 때만.
- 시각·네트워크·실행기는 주입 가능하게 유지(현재 구조 유지).
- 데이터는 서버 50대 규모를 전제로 SQLite 유지, 이력 증가 시 보관 정책(1년)과 함께 점검.

| # | 결정 | 권고 | 영향 |
|---|---|---|---|

| D-3 | 알림 채널(이메일/Teams/Slack/KakaoWork 등)과 담당자 지정 방식(서버별·그룹별) | 이메일 우선, 웹훅 추가 | 0-5, 1-3 |
